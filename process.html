Design process — how I actually work

Before a pixel, the problem gets named.

Not a case study — a working reference. Five starting points, the checklist I run before designing anything, what happens when the brief is vague, and where analytics/feedback/research each earn their place.

01Solve the problem

Not ship the feature that was named — the friction underneath it.

02Find where flows break

Before launch when possible, from real behavior after.

03Wants vs. needs

What a user asks for and what actually removes their friction aren't always the same thing.

04Align with business — on the record

Push back when the metric being optimized costs trust. Named, not implied.

A real negotiation, not a hypothetical

Business wanted clicks on a feature at any cost. I argued against the dark-pattern version: users notice when they were tricked into a click, and that erodes trust faster than the click was worth. We optimized for the metric that compounds instead of the one that spikes once.

Where an engagement actually starts

Five starting points, five different jobs

Treating "adopt their system" and "build one from scratch" as the same task is the mistake — each has its own definition of done, and the wrong one wastes the client's time confirming something that was never in question.

Path 1Adopt as-is

They hand me real tokens, a repo, or Figma variables. Success = exact fidelity to what exists — zero new tokens, nothing of mine leaks in. If something's missing, I ask for it, I don't invent it.

Path 2Extend

Real gaps in their system — a missing state, a component they never built. I extend using their tokens and conventions so the addition doesn't read as bolted-on later.

Path 3Revamp

Only when explicitly asked to modernize. Full pipeline applies, but validated against what they approve as direction — never a surprise on delivery day.

Path 4From scratch

Nothing exists — a brief or brand kit only. Screenshot/Figma/live-site/brand-kit are the four real entry points; still constrained by WCAG and the brief, not a blank check.

Path 5Consolidate

Multiple teams already vibe-coded their own version of "the same" system. The job isn't creating a sixth one — it's picking a single real owner without breaking what already ships.

Day zero with their stack

Starting from images alone, on their tools

If a company hands over screenshots instead of a file — Claude Design, Claude Code, Figma, maybe Framer, maybe a thin design system — none of that blocks day one.

Extract first, build second

Open every image and write down colors, spacing, radius, type scale, and component inventory before touching a tool. This is the same visual-vocabulary pass regardless of which tool receives it next.

Then route to their tool

Figma → variables first, components second. Claude Design → import the extracted tokens before generating anything, one or two passes. Framer → same token set, their component model.

Claude Design — canvas, import DS first Claude Code — code-native, DS enforced in prompt Figma — variables → components Framer — same tokens, their model Basic/partial DS — extend, don't replace
Before designing anything

The discovery checklist

Said out loud in two minutes, not filled out in silence. If two or three of these come back empty, that absence is the actual finding.

  1. 1
    What's the problem, in one sentence?Not the feature — what happens if nothing is done.
  2. 2
    Who has it, specifically?A real segment, not "the user." Rapid segmentation beats inventing a persona.
  3. 3
    What's the real situation today?How it's handled now — by hand, another tool, or not at all.
  4. 4
    Is there a JTBD?"When [situation], I want [motivation], so I can [outcome]." If missing, ask — never invent it.
  5. 5
    Are there written requirements?If vague or absent, that triggers the MVP protocol below.
  6. 6
    Feature priority — which one actually blocks the user?Not the one business mentions first.
  7. 7
    Design system constraintsFull / partial / none — decides which of the five starting points applies.
  8. 8
    Technology constraintsReal stack, who approves layout, who implements.
The question they keep asking in interviews

"What if the requirements list is vague?"

Try to complete it with whoever gave it

Specific questions from the checklist above — never a generic "can you elaborate," which just produces the same vague answer again.

If that's not possible, propose an MVP

The smallest defensible interpretation of what the ticket was minimally trying to solve — delivered, explicitly marked "minimum interpretation, to confirm."

Golden rule — have a default ready, don't start blank under time pressure

Example: "we need a form for X" with nothing else specified.

Minimum fields (adjust to the real domain): - Identity: name, email/phone — the minimum to follow up - The request itself: 1 open field + max 2 structured fields (more than 3 required fields in v1 tanks completion) - Confirmation: what happens after submit (a message, not just a toast) States: empty / inline validation error / submitting / success / network error. Without all 5, the form isn't done even if the fields are. Ask before adjusting the default: 1. Who sees the result, and what do they do with it? 2. Is there already a similar form in production? Adapt that one.
Not project-specific — the general rule

Analytics, feedback, and UXR aren't the same tool

Analytics measures what happened, after the fact. Feedback is what people say unprompted. UXR is what you discover by asking or observing with intent. Instrumenting analytics before the JTBD is clear is the most common way to end up tracking clicks that answer no real question.

MomentWhat runsWhy here, not elsewhere
StartUXR — rapid segmentation + JTBD. Historical feedback if it exists.Nothing exists yet to measure.
MiddleUXR — Lab 0 (paper) → Lab 1 (no audience) → Lab 2 (real people, if time/budget allow).Validate before paying the cost of instrumenting something that may still change.
LaunchAnalytics — real instrumentation. Feedback — live channel now that real users exist.Instrumenting earlier means guessing which event will matter.
2+ weeks inReal reporting (funnels, retention, errors) + accumulated feedback + follow-up UXR when a number doesn't explain the why.A number says what happened; never why.
If the call turns into a live challenge

The first fifteen minutes, in order

Identify which of the five paths this is

High probability it's Adopt or Extend if they hand over real tokens — confirmed before writing a line of CSS.

Map their tokens to a known shape

Background, nav, card, text, accent, radius, density, shadow — never inventing a missing token, asking for it instead.

Pick exactly one tool for the job

Editing a live repo → their code editor of choice. Deciding a layout before code → a canvas tool. Never three tools in a timed exercise.

Run the discovery checklist out loud

Problem, user, JTBD — even under a clock, skipping this produces a prettier wrong answer faster.
